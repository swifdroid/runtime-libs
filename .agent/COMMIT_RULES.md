# Commit Rules

Git, staging, history, and publishing safety for `core-libs`.

## Baseline and Scope

Before mutation, define exact approved paths and record:

```bash
git status --short --untracked-files=all
git branch --show-current
git rev-parse HEAD
```

Treat all pre-existing staged, unstaged, and untracked state as user work unless the current task explicitly establishes otherwise.

- Do not add, edit, delete, rename, move, format, stage, unstage, revert, or otherwise touch files outside approved scope.
- Preserve existing staging boundaries.
- Never use broad cleanup/formatter/generator commands that can mutate unrelated paths without explicit approval.
- If approved paths overlap with user edits that cannot be preserved safely, stop and report the conflict.

## Forbidden Git Mutations by Default

Never stage, commit, tag, push, publish, reset, checkout/restore files, clean, stash, amend, rebase, squash, cherry-pick, or otherwise rewrite/rearrange work/history unless explicitly authorized for the exact operation and target.

A request to implement/test/audit is not commit authorization. Commit authorization is not push/tag/publication authorization.

## Staging

When staging is explicitly authorized:

- stage only approved task-scope changes;
- avoid `git add -A`, `git add .`, `git add -u`, or equivalent broad staging when unrelated work exists;
- prefer exact paths/hunks;
- verify the staged diff before committing.

Required pre-commit inspection:

```bash
git status --short --untracked-files=all
git diff --cached --check
git diff --cached
```

## Commit Atomicity

Keep each commit logically coherent. Do not combine an intended runtime/module change with unrelated cleanup, generated output, local environment state, or pre-existing user work.

A cross-repository SwifDroid task still requires a separate `core-libs` commit. There is no parent workspace commit that can atomically include sibling repositories.

## Commit Subject Style

Follow the dominant maintainer-authored `core-libs` history.

Canonical shape:

```text
<semantic emoji> <concise English action>
```

Rules:

- English only.
- Exactly one meaningful leading emoji followed by one space.
- Short action-oriented subject such as `Add`, `Update`, `Fix`, `Remove`, `Move`, `Implement`.
- Optional scope through `:`, e.g. `Settings: ...` or a concrete module/script scope when useful.
- Put Swift/API symbols, filenames, module/library names, flags, and versions in backticks when appropriate.
- No trailing period.
- Do not use `feat:`, `fix:`, `chore:`, `docs:`, or other Conventional Commit prefixes by default.
- Do not prefix with `core-libs:` or `SwifDroid:` merely to identify the repository.
- Do not append contributor-integration suffixes such as `(#54 by @name)` to ordinary local commits.
- Never add `Generated by Luna-Max`, `Co-authored-by ChatGPT`, AI disclosure, model/tool attribution, or similar boilerplate.

### Established Emoji Semantics

The current `core-libs` maintainer history strongly supports:

- `🪚` - implementation/build/package/script changes and runtime-library updates.
- `🔧` - configuration/fix/targeted compatibility adjustments.
- `📖` - README/changelog/repository documentation updates.
- `🧹` - removal/cleanup of redundant files or configuration.
- `🧪` - approved modern extension for new test-only/verification-only commits; do not claim it is a historically dominant `core-libs` convention if history does not show that.

Representative historical subjects:

```text
🔧 Settings: remove `compression` module
📖 Update readme
📖 Update changelog
🪚 Update `copy-so-files.sh`
🧹 Remove redundant .so files
🪚 Update all `.so` files to official Swift `6.2.0`
```

Choose semantics from this repository's history rather than importing another project's emoji taxonomy.

## Generated/Binary State

Do not commit build caches, local IDE state, SDK/toolchain caches, or generated output unless explicitly part of the deliverable.

Runtime `.so` files are intentional repository inputs when an approved runtime update requires them, but verify exact provenance/version and expected module membership before commit.

## Post-Commit Verification

After an authorized commit, inspect:

```bash
git show --stat --oneline --decorate -1
git status --short --untracked-files=all
```

Confirm the subject style, exact committed scope, preservation of unrelated work, and absence of unexpected generated/local files.

## Publishing

Build success or commit creation never authorizes tag/release/JitPack/publication/push. Each requires separate explicit maintainer authorization.

## Final State

After work, re-check status/branch/HEAD and report only actual repository state.
